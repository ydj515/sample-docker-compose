# Prompt Writing Guide

## 목적

이 문서는 raw prompt를 저장하지 않는 환경에서, `TASK-8`의 간접 지표를 기반으로 프롬프트를 어떻게 개선할지 안내한다.

---

## 기본 원칙

- 프롬프트 원문을 저장하지 않는다.
- 대신 `prompt length`, `output token`, `tool failure`, `retry proxy`, `estimated cost`를 함께 본다.
- 한 개 지표만 보지 말고 최소 2개 이상을 같이 해석한다.

---

## 주요 지표 해석

### 1. prompt length가 길고 output token이 짧다

가능한 의미:

- 배경 설명이 길지만 실제 요청 목적이 흐릿하다.
- 모델이 많은 제약을 읽느라 응답을 짧게 끝낸다.
- 한 번에 너무 많은 맥락을 넣었다.

개선 방향:

- 목표를 1문장으로 먼저 분리한다.
- 출력 형식을 명시한다.
- 배경 설명은 필수 사실만 남긴다.
- 한 턴에서 처리할 범위를 줄인다.

### 2. prompt length가 짧고 retry proxy가 높다

가능한 의미:

- 요청 의도가 부족해서 API/tool 요청이 반복된다.
- 필요한 입력 제약이 빠져 있다.
- 모델이 중간에 여러 번 재탐색한다.

개선 방향:

- 기대 결과를 더 구체적으로 적는다.
- 입력 범위와 성공 조건을 명시한다.
- 모호한 대명사 대신 실제 파일/경로/도메인을 적는다.

### 3. prompt length가 길고 tool failure가 함께 높다

가능한 의미:

- 한 턴에 너무 많은 작업을 몰아넣었다.
- tool이 처리할 범위를 넘어서는 지시가 들어갔다.
- 단계 분리 없이 탐색과 수정을 한 번에 요구했다.

개선 방향:

- 탐색 단계와 수정 단계를 분리한다.
- 실패하기 쉬운 외부 요청은 별도 턴으로 나눈다.
- 성공 기준을 먼저 적고, 실행은 그다음 단계로 분리한다.

### 4. 비용이 높지만 산출 밀도가 낮다

가능한 의미:

- 긴 컨텍스트를 계속 반복해서 넣고 있다.
- 필요한 핵심 문제보다 주변 설명이 더 많다.
- 결과보다 탐색/재시도에 토큰을 많이 쓰고 있다.

개선 방향:

- 매 턴 반복되는 설명을 줄인다.
- 이전 합의는 짧은 bullet로 요약한다.
- 한 번에 요구하는 산출물을 줄인다.

## 추천 프롬프트 패턴

### 문제 해결형

권장 구조:

1. 목표
2. 제약
3. 변경 범위
4. 검증 기준

예시 구조:

```text
목표: TASK-8의 local helper normalizer를 추가해줘.
제약: raw prompt는 저장하지 말고, 기존 scheduler와 PostgreSQL view 패턴을 따라줘.
변경 범위: scripts/, configs/postgres/init/, docs/, dashboards만 수정.
검증 기준: helper turn과 usage/tool/cost가 같은 window로 묶여 Grafana에서 보여야 해.
```

### 코드 리뷰형

권장 구조:

1. 보고 싶은 관점
2. 위험 우선순위
3. 제외할 범위

예시 구조:

```text
이 변경을 review해줘.
버그, 회귀, 성능 리스크를 우선으로 보고, 스타일 코멘트는 뒤로 미뤄줘.
문서 파일은 제외하고 실행 경로와 쿼리만 집중해서 봐줘.
```

### 탐색 후 구현형

권장 구조:

1. 먼저 읽을 대상
2. 구현 목표
3. 완료 기준

예시 구조:

```text
docs/TASK-8.md와 관련 schema/view를 먼저 읽고,
prompt efficiency dashboard를 구현해줘.
완료 기준은 PostgreSQL view와 Grafana dashboard까지 포함이야.
```

## 대시보드 활용 팁

- `Prompt 길이 vs Output Token 상관계수`
  - 너무 낮거나 음수면 긴 프롬프트가 실제 산출 증가로 이어지지 않을 가능성이 있다.
- `Prompt 길이 vs 비용 상관계수`
  - 높을수록 긴 프롬프트가 비용을 직접 밀어 올리는 경향이 있다.
- `Prompt Bucket별 효율 요약`
  - 특정 길이 구간에서 실패율이 튀는지 먼저 본다.
- `고비용 세션 Top 50`
  - 비용이 높은 세션이 실제로 산출도 높은지 같이 본다.
- `개선 후보 Turn`
  - 휴리스틱 기반 추천이므로 반드시 원본 세션 맥락과 함께 해석한다.

---

## Caveats

> - 이 가이드는 prompt 내용 자체가 아니라 간접 지표를 기반으로 한다.
> - `estimated_retry_count`는 정확한 retry counter가 아니라 request 반복 proxy다.
> - `thread_id = conversation_id` 상관관계가 약한 환경에서는 일부 turn 해석이 틀릴 수 있다.
> - raw prompt sampling을 켜지 않는 한, 내용 품질에 대한 직접 평가는 불가능하다.
